# TabZero --- User Journey 1 v0.1

## First Launch → Create Group

This document defines the first-run and group-creation experience for
TabZero.

------------------------------------------------------------------------

## 1. First Launch

The first time TabZero is opened, the user sees a lightweight welcome
screen.

The screen should contain:

> **Welcome to TabZero**
>
> *Split bills, clear the tab. Keep the app free.*
>
> **\[ Create a Group \]**
>
> **\[ Join a Group \]**

The screen should remain intentionally minimal.

There should be no mandatory account creation, login, onboarding
carousel, or lengthy introduction.

------------------------------------------------------------------------

## 2. No Groups State

A newly installed TabZero instance may have no groups.

After the initial screen, if the user has not created or joined a group,
the application should present a simple empty state:

> **No groups yet**
>
> Create or join a group to get started.

Available actions:

-   Create a Group
-   Join a Group

The user can remain in this state indefinitely without being required to
create or join a group.

------------------------------------------------------------------------

## 3. Creating a Group

Selecting **Create a Group** opens a minimal group creation form.

### Required

**Group name**

Example:

> Goa Trip 2026

**Currency**

Example:

> INR ₹

### Optional

**Description**

Example:

> Goa trip with the gang.

The proposed form:

> **Create Group**
>
> Group name \*
>
> `Goa Trip 2026`
>
> Description
>
> `Goa trip with the gang`
>
> Currency \*
>
> `INR ₹`
>
> **\[ Create Group \]**

There is no requirement for globally unique group names.

Multiple groups may have the same name.

------------------------------------------------------------------------

## 4. Creator Identity

When creating their first group, the user is asked for their name.

Example:

> **What's your name?**
>
> `Sayantan`
>
> **\[ Continue \]**

This name represents the user's local/member identity inside the group.

It is **not an account**.

There is:

-   No username
-   No password
-   No email requirement
-   No global profile
-   No account registration

The name simply identifies the member associated with the current
installation.

------------------------------------------------------------------------

## 5. Automatic Creator Membership

After successfully creating a group:

-   The creator becomes a member automatically.
-   The creator becomes the **Super Admin**.
-   The creator's member identity is immediately active.
-   The creator can begin using the group without waiting for anyone
    else.

Example:

> **Goa Trip 2026**
>
> Sayantan
>
> **Super Admin**

------------------------------------------------------------------------

## 6. Initial Group Screen

Immediately after creation, the user should arrive at the new group's
main screen.

A lightweight initial state could show:

> **Goa Trip 2026**
>
> Sayantan · Super Admin
>
> **Members**
>
> Sayantan
>
> **\[ Add Member \]**
>
> **\[ Invite People \]**
>
> **\[ Add Expense \]**

The interface should make the three obvious next actions:

1.  Add members
2.  Invite people
3.  Add an expense

The creator does not need to complete any setup wizard before using the
group.

------------------------------------------------------------------------

## 7. Adding Members Manually

The creator/Admin can manually add people who have not yet installed or
joined TabZero.

Example:

> **Add Member**
>
> Name:
>
> `Rahul`
>
> **\[ Add \]**

The newly created member immediately becomes:

> **Active + Unclaimed**

This is intentional.

An unclaimed member is still a fully usable group member for the purpose
of recording expenses.

For example, Sayantan can immediately create:

> Dinner --- ₹2,000
>
> Paid by: Sayantan
>
> Split among:
>
> Sayantan Rahul Priya

even if Rahul and Priya have never installed TabZero.

------------------------------------------------------------------------

## 8. Unclaimed Member Badging

TabZero should introduce a clear visual distinction between members who
are connected to an approved device and members who have not yet claimed
their identity.

For example:

> Sayantan\
> **Active**

> Rahul\
> **Active · Unclaimed**

> Priya\
> **Active · Unclaimed**

The exact visual treatment can be designed later, but the state should
be immediately understandable.

Possible badge concepts include:

-   `Unclaimed`
-   `Not connected`
-   `Awaiting device`

The preferred terminology for the product specification is:

> **Active · Unclaimed**

This indicates that:

-   The member is an active participant in the group.
-   Their identity exists in the group.
-   No approved device is currently associated with them.

Once the member successfully joins and their identity claim is approved,
the unclaimed badge disappears.

------------------------------------------------------------------------

## 9. Adding Expenses Before Members Join

A group does not need every member to have TabZero installed before
expenses can be recorded.

For example:

> Group: Goa Trip 2026
>
> Members: - Sayantan --- Active - Rahul --- Active · Unclaimed - Priya
> --- Active · Unclaimed

Sayantan can create:

> **Dinner**
>
> ₹2,000
>
> Paid by: Sayantan
>
> Split among: - Sayantan - Rahul - Priya
>
> Equal

The resulting balances are immediately calculated.

When Rahul later installs TabZero and claims the existing Rahul member
identity, his existing historical participation remains intact.

------------------------------------------------------------------------

## 10. Adding an Expense Without Other Members

The creator can add an expense immediately after creating the group,
even if no other members have been added.

Example:

> Dinner
>
> ₹500
>
> Paid by: Sayantan
>
> Split among: Sayantan

This is valid.

The application should not force the user to complete member setup
first.

------------------------------------------------------------------------

## 11. Invite Link Creation

An invite link is automatically created when the group is created.

The creator does not need to manually generate one.

The group should expose an action such as:

> **\[ Invite People \]**

which opens the sharing flow.

The invite link should:

-   Identify the group
-   Contain a sufficiently random secret/token
-   Not expose sensitive group data
-   Be revocable
-   Be regeneratable

The exact token and synchronization mechanism will be defined later.

------------------------------------------------------------------------

## 12. Invite Link Management

Administrators should be able to:

-   Share the current invite link
-   Regenerate the invite link
-   Revoke/disable the invite link

Regenerating the link should invalidate the previous link where
technically appropriate.

This prevents an old invitation from remaining permanently usable after
it has been widely shared.

------------------------------------------------------------------------

## 13. Group Name Uniqueness

Group names are not globally unique.

Users may create multiple groups with identical names.

For example:

> Goa Trip

and:

> Goa Trip

can both exist.

Group identity must therefore rely on an internal unique identifier
rather than the displayed name.

------------------------------------------------------------------------

## 14. Group Archiving

The initial group lifecycle supports:

> **Active → Archived**

The Super Admin can archive the group.

Archiving should remove the group from the normal active-group
experience while preserving its data.

An archived group should remain accessible for:

-   Viewing
-   Export
-   Historical reference
-   Potential future restoration, if supported

Archiving should not immediately destroy data.

------------------------------------------------------------------------

## 15. Permanent Group Deletion

Permanent deletion is intentionally more difficult than archiving.

For v0.1, the preferred future flow is:

> **Export → Explicit Delete Confirmation → Permanent Deletion**

The application should strongly distinguish:

**Archive**

from:

**Delete permanently**

The exact permanent-deletion rules and confirmation flow will be
finalized later.

------------------------------------------------------------------------

## 17. Design Principles Established by Journey 1

Journey 1 establishes several important TabZero principles:

### No forced setup

A user can create a group and immediately record an expense.

### No account creation

The creator's name is a group/member identity, not an account.

### Unclaimed members are valid members

A person does not need the application installed before they can
participate in the group's expense ledger.

### Invitation is automatic

Every newly created group has an invite mechanism available immediately.

### Group names are descriptive, not identifiers

Internal IDs must be independent of displayed names.

### Archive before destruction

Normal group lifecycle should favor preservation over deletion.

### Minimal onboarding

The user should reach a useful state within seconds rather than being
taken through a lengthy setup process.

------------------------------------------------------------------------

## 18. Open Questions Deferred to Later Journeys

The following are intentionally not finalized in Journey 1:

-   Exact group-preview information shown through an invite
-   Membership request states
-   Existing-member claim mechanics
-   Admin approval UX
-   Multiple simultaneous member-claim requests
-   Device identity and synchronization
-   Offline conflict resolution
-   Admin transfer details
-   Archived-group restoration
-   Permanent deletion safeguards
-   Exact notification behavior
-   Exact visual design of the `Active · Unclaimed` badge

These will be addressed in subsequent journeys.
