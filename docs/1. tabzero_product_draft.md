# TabZero

### Because splitting a ₹2,000 dinner shouldn't require a subscription. Split bills, clear the tab!

> A deliberately BORING, simple, accountless, local-first expense splitter for
> groups of people who just want to know **who owes whom**.

------------------------------------------------------------------------

## 1. Intent

TabZero is a lightweight Android app inspired by the useful core of
expense-splitting applications, while deliberately leaving out the
complexity, account requirements, subscriptions, advertising, and
unnecessary financial categorization that can get in the way of a simple
shared expense.

The goal is not to build another full-featured personal-finance
platform.

The goal is:

> **Record what happened. Calculate who owes whom. Settle up. Done.**

There are no user accounts.

There is no mandatory cloud account.

There are no spending categories.

There is no complicated budgeting system.

There is no subscription required to unlock the basic functionality.

And there is absolutely no reason to turn splitting a dinner bill into a
SaaS product.

------------------------------------------------------------------------

## 2. Product Philosophy

TabZero follows a few simple principles.

### 2.1 No accounts

A user should be able to install the app and start using it immediately.

Identity is intentionally lightweight.

A person inside a group is represented by a **member**, initially
identified simply by a name.

The device using the app is separate from that logical identity.

This allows a group to exist without requiring every participant to
create an account.

------------------------------------------------------------------------

### 2.2 Local-first

The app should work perfectly without an internet connection for
everything that can reasonably be done locally.

Users should be able to:

-   Create groups
-   Add members
-   Record expenses
-   Record settlements
-   Calculate balances
-   Simplify debts
-   View history
-   Export group data

without depending on a server.

Internet connectivity is primarily required when people need to interact
with other devices, such as joining a group through an invite link or
requesting ownership of an existing member.

------------------------------------------------------------------------

### 2.3 The data belongs to the group

A group is the logical owner of its expense history.

It should not fundamentally depend on the device of the person who
originally created it.

The group can therefore be:

-   Shared with others
-   Exported
-   Imported
-   Archived
-   Cloned

without changing the meaning of its financial history.

------------------------------------------------------------------------

### 2.4 Transactions are the source of truth

The app should never treat a calculated balance as the authoritative
data.

The source of truth is always the transaction history.

For example:

**Expense**

-   Amount: ₹1,000
-   Paid by: Sayantan
-   Split between: Sayantan, Rahul, Priya, Amit
-   Split: Equally

and:

**Settlement**

-   Amount: ₹250
-   From: Rahul
-   To: Sayantan

Balances are calculated from these transactions.

The architecture therefore follows:

**Transactions → Balances → Simplified debts → UI**

This keeps calculations deterministic and prevents stored balances from
becoming inconsistent with the underlying history.

------------------------------------------------------------------------

# 3. Core Concept

The application revolves around four primary concepts:

1.  **Groups**
2.  **Members**
3.  **Expenses**
4.  **Settlements**

Everything else exists to make these four concepts easy to manage.

------------------------------------------------------------------------

# 4. Groups

Users can create any number of groups.

Examples:

-   Goa Trip 2026
-   Flat Expenses
-   Office Lunch
-   Weekend Trip
-   Friends
-   Family

A group contains:

-   Group name
-   Optional description
-   Members
-   Expenses
-   Settlements
-   Admin(s)
-   Invite mechanism
-   Creation information
-   Active/archived state

There is no practical restriction on the number of groups.

------------------------------------------------------------------------

# 5. Group Access

Groups are not intended to be publicly searchable.

Instead, they use a **link-access model**.

Anyone who possesses a valid invite link can request to join.

The invite mechanism should use a sufficiently random secret/token
rather than relying solely on a predictable group ID.

Administrators can:

-   Generate an invite link
-   Regenerate an invite link
-   Disable an invite link
-   Approve membership requests

The distinction is important:

> **The group data is private; the invitation mechanism is shareable.**

------------------------------------------------------------------------

# 6. Member Identity

A member is a logical person inside a group.

A member can initially exist without being connected to an app
installation.

For example, an administrator may create:

-   Sayantan
-   Rahul
-   Priya
-   Amit

before any of those people install the application.

These are **unclaimed members**.

This allows someone to keep accurate records even when only one person
is currently using the app.

------------------------------------------------------------------------

# 7. Joining an Existing Group

When somebody follows an invitation link, the application asks:

> **Are you already a member of this group?**

### Existing member

The user can select:

> **Yes, I'm already a member**

They then select the existing member identity, for example:

> Rahul

The administrator receives a membership claim request:

> Rahul wants to claim the existing member **Rahul** on this device.

The administrator can:

-   Approve
-   Reject

The app should never silently replace an existing member.

------------------------------------------------------------------------

### New member

Alternatively:

> **No, I'm a new member**

The user provides their name and requests membership.

The administrator approves the new member.

------------------------------------------------------------------------

# 8. Members Are Not Automatically Deleted

A member with historical transactions should not simply disappear.

For example:

> Rahul owes ₹2,000.

The administrator should not be able to delete Rahul and thereby destroy
the meaning of the historical records.

Instead, members can be **archived**.

Archived members remain attached to historical transactions but are no
longer active participants in new expenses.

If necessary, the application can require outstanding balances to be
settled or explicitly transferred before a member is archived.

------------------------------------------------------------------------

# 9. Roles

Keep roles intentionally simple.

## Admin

An administrator can:

-   Manage members
-   Approve membership requests
-   Approve member claims
-   Manage invite links
-   Archive the group
-   Perform administrative actions on group data

## Member

A member can:

-   View the group
-   Add expenses
-   View balances
-   Add settlements
-   Participate in expense splits
-   Edit their own expenses, subject to the application's rules

Administrative deletion of other people's transactions should preferably
remain restricted.

------------------------------------------------------------------------

# 10. Expenses

An expense contains only the information required to calculate the
resulting debt.

### Required

-   Description
-   Amount
-   Paid by
-   Split among

### Optional

-   Date/time
-   Note

There are deliberately **no expense categories**.

No:

-   Food
-   Travel
-   Shopping
-   Entertainment
-   Bills
-   Custom categories

The app is not trying to become a personal finance manager.

It answers one question:

> **Who paid, and who should share the cost?**

------------------------------------------------------------------------

# 11. Splitting

By default, an expense is split equally among all active group members.

Example:

> Dinner --- ₹1,000\
> Paid by Sayantan\
> Split among 4 members\
> Equal split

Result:

-   Sayantan: ₹250
-   Rahul: ₹250
-   Priya: ₹250
-   Amit: ₹250

Sayantan has effectively paid ₹750 on behalf of everyone else.

------------------------------------------------------------------------

## 11.1 Selective Splitting

The user can select exactly which members participate in an expense.

All active members are selected by default.

Members can be toggled on/off using checkboxes/ticks.

Example:

> Dinner --- ₹1,000\
> Paid by Sayantan\
> Split among: Sayantan, Rahul, Priya

Amit does not participate and therefore owes nothing for that expense.

------------------------------------------------------------------------

## 11.2 Unequal Splitting

The application supports unequal splits.

Example:

> Dinner --- ₹1,000

-   Sayantan --- ₹100
-   Rahul --- ₹200
-   Priya --- ₹300
-   Amit --- ₹400

The application must ensure that the individual allocations add up
exactly to the expense total.

------------------------------------------------------------------------

# 12. Settlements

Expenses and settlements are separate transaction types.

An expense records:

> **Someone paid for something.**

A settlement records:

> **Someone paid another member back.**

Example:

> Rahul → Sayantan\
> ₹250

Settlements are first-class transactions and remain part of the group's
history.

No payment gateway or UPI integration is required.

The app records the fact that the members consider the debt settled.

------------------------------------------------------------------------

# 13. Balances

Balances are derived from all applicable expenses and settlements.

The application should present both:

### Individual balance

> **Sayantan**
>
> You are owed ₹750.

and:

### Debt relationships

> Rahul owes Sayantan ₹250\
> Priya owes Sayantan ₹250\
> Amit owes Sayantan ₹250

The exact UI can evolve, but the underlying calculation must always come
from transactions.

------------------------------------------------------------------------

# 14. Simplify Debts

The application should support debt simplification.

The purpose is to reduce the number of actual repayments required while
preserving the overall financial result.

Example:

Before simplification:

-   Rahul → Sayantan ₹500
-   Priya → Rahul ₹300
-   Amit → Sayantan ₹200
-   Priya → Amit ₹100

The application can derive a simpler set of repayments.

For example:

-   Priya → Sayantan ₹400
-   Amit → Sayantan ₹300

The exact simplification algorithm is an implementation detail.

The important principle is:

> **Simplification changes the presentation of what should be paid, not
> the underlying transaction history.**

The original expenses and settlements remain untouched.

------------------------------------------------------------------------

# 15. Editing and Deleting Expenses

Expenses should support:

-   View
-   Edit
-   Delete

Each expense should retain enough metadata to understand:

-   Who created it
-   When it was created
-   When it was last modified

Deleting an expense should require confirmation.

Internally, deletion should preferably be represented in a way that
preserves consistency and allows the application to reason about history
rather than simply destroying data without trace.

------------------------------------------------------------------------

# 16. Import / Export

A group can be exported as JSON.

The export should contain the complete information required to
reconstruct the group's state, including:

-   Group information
-   Members
-   Membership state
-   Expenses
-   Settlements
-   Relevant metadata
-   Schema/version information

The exported JSON is intended to be portable and human-readable.

------------------------------------------------------------------------

# 17. Read-only Import

Imported group data is **always read-only**.

This is a deliberate design decision.

For example:

> Imported: `Goa Trip 2026.json`
>
> **READ ONLY**
>
> Imported on: 18 Aug 2026

The user can:

-   View the group
-   View expenses
-   View settlements
-   View balances
-   View historical information

The user cannot directly modify the imported data.

This prevents an imported historical snapshot from being mistaken for
the authoritative current group.

------------------------------------------------------------------------

# 18. Clone Imported Group

A read-only imported group can optionally be **cloned**.

For example:

`Goa Trip 2026.json`

↓

**Clone as new group**

↓

`Goa Trip 2027`

The cloned group becomes a completely independent editable group.

It has no live relationship with the original imported data.

------------------------------------------------------------------------

# 19. Reinstallation

Because there are no accounts, reinstalling the application means the
application cannot magically recover local data.

This is intentional.

The primary recovery mechanism is:

> **Export → Reinstall → Import**

Imported data remains read-only unless explicitly cloned.

Shared groups can also be rejoined through their invitation mechanism,
subject to membership verification/approval.

------------------------------------------------------------------------

# 20. Offline Behaviour

The following should work completely offline:

-   Create groups
-   Add members
-   Record expenses
-   Record settlements
-   Calculate balances
-   Simplify debts
-   View history
-   Export data

Network connectivity is required only where communication with another
device/service is necessary.

Examples:

-   Joining a remotely shared group
-   Sending a membership claim
-   Receiving administrator approval
-   Other future synchronization features

------------------------------------------------------------------------

# 21. What TabZero Deliberately Does NOT Do

The first version should resist feature creep.

It does not need:

-   User accounts
-   Passwords
-   Social profiles
-   Expense categories
-   Budgets
-   Personal finance dashboards
-   Bank synchronization
-   Credit cards
-   UPI payments
-   Payment gateways
-   Ads
-   Subscription tiers
-   Premium categories
-   AI financial advice
-   Complicated analytics

The product should remain focused.

> **Split bills. Track debts. Settle up.**

------------------------------------------------------------------------

# 22. Design Philosophy

The application should feel lightweight.

A user should not need a tutorial to record:

> ₹800 → Sayantan paid → 4 people → Equal

The most common action should require very few interactions.

Defaults should do the right thing:

-   All active members selected
-   Equal split selected
-   Current date selected
-   One payer selected
-   Amount entered directly

Advanced options should be available without becoming the default
experience.

------------------------------------------------------------------------

# 23. Data Model Principle

The conceptual data flow should remain:

``` text
Groups
   │
   ├── Members
   │
   ├── Expenses
   │      │
   │      ├── Payer
   │      ├── Participants
   │      └── Allocations
   │
   └── Settlements
          │
          ├── From
          └── To

             ↓

        Transaction Ledger

             ↓

          Balances

             ↓

       Simplified Debts

             ↓

             UI
```

The ledger is the source of truth.

Balances are derived.

Simplified debts are derived.

The UI never becomes the source of financial truth.

------------------------------------------------------------------------

# 24. Product Personality

TabZero should have a slightly irreverent personality.

Not obnoxious.

Not childish.

Just enough sarcasm to make the product feel different from conventional
expense apps.

Possible messaging:

> **Split bills, not subscriptions.**

> **Your friends owe you money. The app doesn't need to.**

> **No account. No premium tier. No nonsense.**

> **₹500 dinner. ₹0 subscription.**

> **Track your debts. Not your spending habits.**

> **Because splitting a pizza shouldn't require a financial ecosystem.**

The core tagline should remain:

## **Split bills, not subscriptions.**

### Members

-   Unclaimed members
-   New member requests

-   Amount
-   Payer

-   Equal split
-   Unequal split

-   Optional note

### Settlements

-   Settlement history

### Balances

-   Debt relationships

### Data portability

-   Offline-capable

# 26. Guiding Principle

If a proposed feature does not make it easier to answer:

> **"Who owes whom, and how much?"**

it probably does not belong in the core application.
