# TabZero — User Journey 6 v0.1
## Offline / Sync / Conflicts / Reinstallation

This document defines TabZero's local-first behavior, synchronization model, offline operation, conflict handling, device recovery, JSON portability, and backend philosophy.

The central principle:

> **TabZero should work perfectly without internet. The internet should primarily synchronize, not enable the core experience.**

---

## 1. Local-First Architecture

TabZero always reads from the local database first. Opening a group never requires waiting for the server.

```text
Open TabZero
     ↓
Local database
     ↓
Instant UI
     ↓
Background sync
     ↓
Update if necessary
```

## 2. First-Time Group Join

When a user joins a group for the first time, the device obtains the group's current state from the backend. After initial synchronization, the group can be used offline.

## 3. Local Copy Per Group

Every group the device has accessed has a complete local working copy containing everything necessary to display the group, calculate balances, create expenses and settlements, perform locally authorized edits, and export JSON.

## 4. Server as Source of Truth

For synchronized groups:

> **Local database = local working state**  
> **Server = authoritative shared state**

The server is authoritative for membership, roles, group status, device authorization, administrative permissions, accepted financial operations, and synchronization state.

## 5. Stable Transaction IDs

Every expense and settlement has a globally unique immutable ID generated locally so transactions can be created offline.

## 6. Device ID

Each TabZero installation receives a random unique Device ID. It distinguishes installations but is not an account or user-facing identity.

## 7. Member ID

Every member receives a stable immutable Member ID. Display names are presentation only.

## 8. Group ID

Every group receives a stable random Group ID. Displayed names are not identifiers.

## 9. Immutable IDs

The following never change:

- Group ID
- Member ID
- Device ID
- Expense ID
- Settlement ID

## 10. Operation-Based Synchronization

TabZero synchronizes changes/operations rather than repeatedly uploading the entire database.

This reduces bandwidth, backend processing, storage, and synchronization complexity.

## 11. Technical Sync Log

TabZero does not retain an infinite technical synchronization log.

Financial history and activity history remain permanently available. Technical synchronization records may eventually be compacted once no longer necessary.

## 12. Offline Member Name Changes

Member name changes can be performed offline and become pending synchronization operations.

## 13. Offline Expense Editing

Expenses can be edited offline when the user has the required local permission.

The UI immediately reflects the change, for example:

> **Edited · Pending sync**

The backend ultimately validates the operation.

## 14. Offline Expense Deletion

Deleting an expense can be performed offline when the user has the required local permission. The deletion remains pending until synchronization.

## 15. Offline Restoration

Restoring a deleted expense or settlement can be performed offline when the user has the required local permission.

## 16. Permission Changes While Offline

If a user performs an authorized operation while offline and loses the required permission before synchronization, the backend rejects the operation.

The local operation is not silently deleted.

## 17. Permission Conflict Message

The user sees:

> **This change could not be synchronized because your permissions changed.**

## 18. Server-Side Validation

Every incoming operation is validated against current server state. The client cannot grant itself permission.

## 19. Idempotent Synchronization

Every synchronization operation must be idempotent. Retrying an already accepted operation must never create a duplicate.

## 20. Automatic Sync Retry

Failed synchronization automatically retries using backoff. Temporary network failure is not treated as a permanent error.

## 21. Pending Changes Survive App Restart

Pending operations remain in the local database after the app closes and continue when it reopens.

## 22. Pending Changes Survive Device Reboot

Pending operations survive a full Android device reboot.

## 23. Android App Data Clear

If Android application data is explicitly cleared, the local database is destroyed. Recovery requires server synchronization/reclamation or a previously exported JSON snapshot.

## 24. App Reinstallation

After reinstalling:

```text
Install TabZero
      ↓
Join/reclaim group
      ↓
Existing member
      ↓
Approval where required
      ↓
New device association
      ↓
Synchronize group
```

## 25. Recovering Groups After Reinstallation

Groups can be recovered through server-side membership reclamation or JSON recovery.

## 26. Super Admin Reinstallation

Super Admin ownership belongs to the Member + Group relationship, not the physical device. Reclaiming the existing member restores Super Admin status.

## 27. Existing-Member Claim Security

Claiming an existing member never automatically grants access merely because the claimant provides the same display name. The established approval mechanism remains required.

## 28. Super Admin Recovery

If the Super Admin is unavailable, existing Admins can initiate Super Admin recovery.

## 29. Admin Consensus

Recovery requires a **majority of Admins**. A single Admin cannot unilaterally seize ownership.

## 30. No Admins Left

If no Admins remain, a **majority of active claimed members** can elect a new Super Admin.

## 31. Offline Group Creation

A new group can be created completely offline.

## 32. Offline Invite Links

A newly created offline group cannot produce a working server-backed invite link until first synchronization.

> **Invite link available after first sync**

## 33. Offline Member Creation

Members can be added while offline and begin as:

> **Active · Unclaimed**

## 34. Offline Expense Immediately After Group Creation

Creating a group, adding members, adding expenses, calculating balances, and recording settlements can all work offline.

## 35. Initial Sync Strategy

New devices use:

> **Snapshot + incremental operations**

rather than replaying the entire lifetime of technical operations.

## 36. Snapshot and History

The snapshot preserves enough information to reconstruct current state and required permanent history. Technical synchronization records can then be compacted.

## 37. Offline JSON Export

JSON export works completely offline and includes the user's current local state, including pending changes and useful synchronization metadata where appropriate.

## 38. JSON Import

JSON import works offline and is always:

> **Read-only**

## 39. Clone Imported Group

An imported read-only snapshot can be cloned into a new editable local group. When synchronized, it becomes a new server-side group.

## 40. Imported Group Identity

A clone receives a new Group ID and never reuses the original Group ID.

## 41. Imported History

Imported history is preserved, while new activity in the clone begins a separate new timeline.

## 42. Import Into Existing Group

TabZero does not support merging imported JSON into an existing group.

> **Import = read-only snapshot**  
> **Clone = new independent editable group**

## 43. Multiple Devices

A member can have multiple approved devices operating on the same group simultaneously.

## 44. One Device, Multiple Groups

A physical device has one Device ID but may represent the same member across multiple groups.

There is no account logout model.

## 45. Device Identity vs Member Identity

Device identity and member identity remain separate. A device is a technical synchronization identity; a member is the financial/historical identity.

## 46. Device Revocation Scope

Revoking a device is group-specific. Revoking Rahul's device from Goa Trip does not affect Flatmates.

## 47. Device Security

Device authentication credentials and synchronization credentials should use appropriate Android secure storage.

## 48. Server Access After Reinstallation

After reinstalling, previous device credentials are gone. The user must rejoin/reclaim, obtain approval where required, and receive new device credentials.

## 49. JSON Backup

TabZero should encourage periodic JSON export, but never annoyingly. A subtle indication such as:

> **Backup — Last export: 42 days ago**

is preferred over frequent notifications.

## 50. Automatic Backup

Automatic periodic JSON backups are out of scope for v0.1. Manual export is the supported mechanism.

## 51. Sync Status

Normal synchronization remains subtle:

> **Synced**  
> **Syncing…**

Counts are shown only when something actually needs attention.

## 52. Temporary Sync Failure

Temporary network failure is not treated as a major error. TabZero waits and retries.

Meaningful failures include permission denial, conflict, invalid operation, archived group, or server rejection.

## 53. Sync Issues Screen

A dedicated **Sync Issues** screen exists only when unresolved issues exist.

Example:

> ⚠️ **2 items need attention**
>
> Expense edit couldn't be synchronized.
>
> Group was archived before this expense could sync.
>
> **[ Review ]**

## 54. Never Lose User Data

Core principle:

> **Never silently lose a local user operation.**

Every operation ultimately becomes:

- Synced
- Pending
- Rejected with explanation
- Conflict requiring resolution
- Exportable

## 55. Backend Completely Unavailable

If the backend is unavailable, the app continues functioning locally. Users can view groups, add/edit/delete permitted expenses, record settlements, view balances/history, and export JSON.

## 56. Group Join During Server Outage

Joining requires backend access.

> **Can't connect right now.**

No fake local membership request is created.

## 57. Notifications During Server Outage

Server-generated notifications cannot be delivered while the backend is unavailable. Normal notification processing resumes when synchronization returns.

## 58. Ledger as the Source for Derived Values

Expenses + Settlements are the authoritative financial ledger.

Balances, simplified debts, group spending, and individual financial position are derived from the ledger and are not independently authoritative values.

## 59. Backend Philosophy

TabZero is explicitly designed around:

> **A boring monolith.**

v0.1 should avoid unnecessary infrastructure such as Redis, Elasticsearch, message queues, microservices, and heavy analytics.

Conceptually:

```text
Android App
     ↕
Simple API
     ↕
Compact Database
```

The exact backend technology remains a separate architecture decision.

Priority:

> **Cheap, boring, reliable.**

# Journey 6 — Core Rules

- Local-first
- Offline-capable
- Server-authoritative
- Immutable identities
- Idempotent synchronization
- Persistent pending state
- Permission validation at synchronization
- No silent data loss
- Technical log compaction
- Permanent financial/activity history
- Snapshot + incremental synchronization
- Offline JSON export
- Read-only JSON import
- New-ID clone isolation
- No JSON merge
- Device/member identity separation
- Group-scoped device revocation
- Reinstallation recovery
- Super Admin recovery by majority of Admins
- No-Admin recovery by majority of active claimed members
- Offline group creation
- Invite links available after initial synchronization
- Useful operation during backend outages
- Lightweight monolithic backend

# Journey 6 Status

**Status: Defined for v0.1**

TabZero's synchronization philosophy is:

> **Local-first. Server-authoritative. Idempotent. Recoverable.**

The user should never need to care whether a change is currently being synchronized unless something actually requires attention.
