# TabZero --- User Journey 4 v0.1

## Balances → Simplify → Settle → Partial Settlement

This document defines how TabZero turns the transaction ledger into
understandable balances, simplified repayment relationships, and
settlement actions.

The primary question this journey must answer is:

> **Who owes whom, and how much?**

The underlying transaction ledger remains the source of truth
throughout.

------------------------------------------------------------------------

# 1. Group Balance Overview

When opening a group, the primary financial screen should present the
current user's personal position first.

Example:

> # Goa Trip 2026
>
> ### Your balance
>
> **You are owed ₹1,250**
>
> Rahul → You ₹600\
> Priya → You ₹650
>
> ------------------------------------------------------------------------
>
> ### Group
>
> Sayantan is owed ₹1,250\
> Rahul owes ₹600\
> Priya owes ₹650\
> Amit is **Settled up**

This prioritizes the information most relevant to the current user.

------------------------------------------------------------------------

# 2. Human Language Over Symbols

The balance UI should primarily use natural language.

The application should not rely on:

> +₹1,250\
> −₹600

because plus/minus notation may be confusing to non-technical users.

Instead:

> **You are owed ₹1,250**

> **You owe ₹600**

> **Settled up**

The underlying data model may still use signed numerical balances
internally.

The UI should translate those values into human language.

------------------------------------------------------------------------

# 3. Zero Balance

A member with a zero balance is displayed as:

> **Settled up**

rather than simply:

> ₹0

This makes the state immediately understandable.

------------------------------------------------------------------------

# 4. Simplification Default

**Simplify Debts = ON by default.**

The primary balance interface therefore shows the simplified repayment
relationships.

Example:

> Rahul → Sayantan ₹200\
> Rahul → Priya ₹300

rather than every raw debt relationship.

The simplification algorithm preserves every member's net balance while
attempting to minimize the number of repayments.

------------------------------------------------------------------------

# 5. Simplification Preference

The Simplify setting is remembered **per group**.

Example:

> Goa Trip 2026 → Simplify ON
>
> Flatmates → Simplify OFF

Changing the setting in one group does not affect other groups.

------------------------------------------------------------------------

# 6. Ledger Independence

Simplification changes only the displayed/recommended repayment
relationships.

It does not modify the underlying transaction ledger.

The fundamental rule is:

> **The UI changes. The ledger does not.**

No simplification operation creates, modifies, or deletes expenses or
settlements.

------------------------------------------------------------------------

# 7. "How Is This Calculated?"

A simplified repayment relationship should have a small informational
icon.

Example:

> Rahul → Priya ₹300 ⓘ

Tapping the icon opens a lightweight explanation:

> **How is this calculated?**
>
> Rahul owes Sayantan ₹500.
>
> Sayantan owes Priya ₹300.
>
> To reduce the number of repayments, TabZero suggests:
>
> **Rahul → Priya ₹300**
>
> This does not create a new transaction.

The explanation is optional and does not clutter the main balance
screen.

------------------------------------------------------------------------

# 8. Simplification Does Not Create Transactions

A displayed relationship such as:

> Rahul → Priya ₹300

is only a recommended repayment.

It is **not** a Settlement transaction.

Only when a user records:

> Rahul → Priya ₹300

does an actual Settlement transaction exist in the ledger.

This distinction must remain explicit throughout the application.

------------------------------------------------------------------------

# 9. Settle Up

When a user selects a debt relationship:

> Rahul owes Sayantan ₹600

TabZero automatically proposes:

> **Settle Up**
>
> Rahul → Sayantan
>
> Amount: **₹600**
>
> **\[ Record Settlement \]**

The payer and recipient do not need to be manually selected.

The application derives them from the debt relationship.

------------------------------------------------------------------------

# 10. Immediate Balance Update

After recording a settlement, the balance updates immediately.

Example:

Before:

> Rahul owes Sayantan ₹600

Rahul pays:

> ₹300

After recording:

> Rahul owes Sayantan ₹300

No manual refresh action is required.

The local ledger is updated first, and derived balances are recalculated
immediately.

------------------------------------------------------------------------

# 11. Who Can Record a Settlement

Any active member can record a settlement.

Example:

> Rahul pays Sayantan ₹300.

Rahul can record it.

Sayantan can also record:

> Rahul → Sayantan ₹300

on Rahul's behalf.

Another member can also record the transaction if appropriate.

The application does not require the person who actually paid to be the
person entering the transaction.

------------------------------------------------------------------------

# 12. Settlement Confirmation

Before recording a settlement, TabZero shows a confirmation.

Example:

> **Record settlement?**
>
> Rahul → Sayantan
>
> ₹300
>
> This will reduce Rahul's outstanding balance.
>
> **\[ Cancel \]** **\[ Record Settlement \]**

Settlement confirmation is required because a settlement directly
changes calculated balances.

------------------------------------------------------------------------

# 13. Settlement Date and Timestamp

Settlements have:

-   Expense/settlement date
-   Exact creation timestamp

The UI displays the date by default.

The exact timestamp remains stored internally.

Future settlement dates are allowed.

Example:

> Settlement date: 20 Aug 2026
>
> Created at: 18 Aug 2026, 11:42 PM

------------------------------------------------------------------------

# 14. Settlement Notes

Settlements support an optional note.

Example:

> `Cash paid at dinner 💵`

Settlement notes follow the same text rules as expense notes:

-   Plain text
-   Emoji
-   New lines
-   No rich text

Pasted rich content is converted to plain text.

------------------------------------------------------------------------

# 15. Settlement History

Settlement history distinguishes the financial relationship from the
person who entered the transaction.

Example:

> **Settlement recorded**
>
> Rahul → Sayantan ₹300
>
> Recorded by Sayantan

This makes it clear that:

-   Rahul is the payer
-   Sayantan is the recipient
-   Sayantan entered the transaction

------------------------------------------------------------------------

# 16. Settlement Editing

Settlement editing follows the same permission model as expenses.

### Creator

Can edit their own settlement.

### Admin / Super Admin

Can edit any settlement.

### Other members

Read-only.

This keeps the transaction-management model consistent.

------------------------------------------------------------------------

# 17. Settlement Deletion

A settlement can be deleted by:

-   Its creator
-   Admin
-   Super Admin

Deletion:

1.  Requires confirmation
2.  Can optionally include a reason
3.  Recalculates balances immediately
4.  Remains visible in history

Example:

> ~~Rahul → Sayantan ₹300~~
>
> **Settlement deleted**
>
> Deleted by Sayantan

------------------------------------------------------------------------

# 18. Settlement Restoration

Deleted settlements can be restored.

Only Admin/Super Admin can restore a deleted settlement.

Example:

``` text
Deleted Settlement
        ↓
      Restore
        ↓
Active Settlement
        ↓
Balance recalculated
        ↓
History updated
```

Restoration itself appears in history.

------------------------------------------------------------------------

# 19. Overpayment

TabZero allows overpayment but warns the user.

Example:

Rahul owes Sayantan:

> ₹500

The user attempts:

> ₹700

TabZero displays:

> ⚠️ **This is ₹200 more than Rahul currently owes Sayantan.**
>
> Are you sure?
>
> **\[ Cancel \]** **\[ Record ₹700 \]**

If confirmed, the transaction is recorded normally.

The resulting balance may reverse the debt relationship.

For example:

> Sayantan owes Rahul ₹200

The ledger remains authoritative.

------------------------------------------------------------------------

# 20. Settling a Simplified Debt

A settlement can follow a simplified repayment recommendation.

Example:

Raw relationships:

> Rahul → Sayantan ₹500\
> Sayantan → Priya ₹300

Simplified recommendation:

> Rahul → Sayantan ₹200\
> Rahul → Priya ₹300

If Rahul selects:

> Rahul → Priya ₹300

TabZero records the actual Settlement transaction as:

> Rahul → Priya ₹300

The Settlement does not need to reference the specific expenses that
generated the recommendation.

It simply becomes another ledger transaction.

------------------------------------------------------------------------

# 21. Post-Settlement Simplification

After any settlement, TabZero immediately recalculates:

-   Member balances
-   Debt relationships
-   Simplified repayments

The UI updates immediately.

There is no manual refresh action.

------------------------------------------------------------------------

# 22. Fully Settled Group

If all members have a net balance of zero:

> 🎉 **All settled.**
>
> Apparently friendship survived accounting.

TabZero can use occasional subtle personality in this state.

The humor should remain restrained and should never interfere with the
financial information.

------------------------------------------------------------------------

Selecting a member opens their balance detail.

Example:

>

>
> Rahul owes:
>
> Sayantan ₹400\
> Priya ₹200
>

>

>
> Dinner ₹300\

The main view remains concise.

Detailed transaction reasoning is available through the member detail

------------------------------------------------------------------------

# 24. Balance Explanation

A user should be able to understand why a balance exists.

Example:

> Rahul owes Sayantan ₹600
>
> **ⓘ How is this calculated?**

Opening the explanation shows the relevant underlying expenses and
settlements contributing to the current balance.

This is important for user trust and dispute resolution.

------------------------------------------------------------------------

# 25. Balance Interpretation

Internally:

**Positive balance**

> Member is owed money.

**Negative balance**

> Member owes money.

**Zero balance**

> Settled up.

The UI translates these into natural language rather than displaying raw
signed numbers.

------------------------------------------------------------------------

# 26. Group Spending Total

The group overview should show how much the group has spent together.

Example:

> **Group spending**
>
> ₹24,850

This is the sum of applicable expenses recorded for the group.

The figure represents total recorded spending, not total outstanding
debt.

It should not be confused with the amount currently owed between
members.

------------------------------------------------------------------------

# 27. Simplification Objective

The simplification algorithm should:

> **Minimize the number of repayments while preserving every member's
> net balance.**

This is the primary optimization objective.

The algorithm must not:

-   Change the ledger
-   Change expense amounts
-   Change settlement amounts
-   Change member balances
-   Create actual Settlement transactions

It only determines an efficient recommended repayment graph.

------------------------------------------------------------------------

# 28. Individual Settlements

Settlement remains an individual member-to-member action.

If:

> Rahul owes Sayantan ₹500
>
> Priya owes Sayantan ₹500

TabZero does not create a group-level:

> "Collect ₹1,000"

operation.

Instead:

> Rahul → Sayantan ₹500
>
> Priya → Sayantan ₹500

Each settlement remains an independent transaction.

------------------------------------------------------------------------

# 29. Settlement Notification

After recording a settlement, the recorder can optionally notify the
relevant member.

Example:

> **Settlement recorded**
>
> Rahul → Sayantan ₹300
>
> **\[ Notify Rahul \]**

The notification is a one-tap optional action.

------------------------------------------------------------------------

# 30. Notification Does Not Verify Payment

A settlement notification means only:

> **A settlement was recorded in TabZero.**

It does not mean:

> TabZero verified the actual payment.

TabZero does not connect to:

-   Banks
-   UPI
-   Payment gateways

The application records the group's stated financial event.

------------------------------------------------------------------------

# 31. Suggested Settlement Actions

TabZero should make settlement actions easily accessible.

Example:

> **You owe Rahul ₹450**
>
> **\[ Settle ₹450 \]**

or:

> **Rahul owes you ₹600**
>
> **\[ Record payment \]**

The app should make the most likely next action one tap away.

------------------------------------------------------------------------

# 32. Balance Refresh

Balances are derived locally and update immediately after every relevant
transaction change.

Relevant changes include:

-   Expense creation
-   Expense edit
-   Expense deletion
-   Expense restoration
-   Settlement creation
-   Settlement edit
-   Settlement deletion
-   Settlement restoration

No manual refresh button is required.

If offline, the local balance updates immediately.

Synchronization happens separately.

------------------------------------------------------------------------

# 33. Offline Settlement

Settlements can be created offline.

They receive a local synchronization state such as:

> ☁️ Pending sync

The settlement immediately affects local balances.

When connectivity returns, it is synchronized with the backend.

------------------------------------------------------------------------

# 34. Concurrent Settlement Transactions

Suppose:

> Rahul owes Sayantan ₹500.

While offline:

Rahul records:

> Rahul → Sayantan ₹300

At approximately the same time, Sayantan records:

> Rahul → Sayantan ₹500

These are **not treated as conflicting edits**.

They are separate Settlement transactions.

Both should be synchronized.

The resulting ledger determines the final balance.

If the combined transactions create an overpayment or reverse the debt
relationship, TabZero reflects that result and can warn about the
resulting balance where appropriate.

The system must not silently discard either transaction.

------------------------------------------------------------------------

# 35. Possible Duplicate Settlement

TabZero v0.1 should detect suspiciously identical settlement
transactions and warn the user.

For example:

> Rahul → Sayantan ₹300

is recorded twice within a very short period.

TabZero may show:

> ⚠️ **Possible duplicate settlement**
>
> A similar settlement was recorded 20 seconds ago.
>
> **\[ Record Anyway \]**

The warning should be based on highly similar properties such as:

-   Same payer
-   Same recipient
-   Same amount
-   Very close timestamps

The system must not automatically block the transaction.

Users retain control.

------------------------------------------------------------------------

# 41. Journey 4 Product Rules

### Human-readable balances

Use natural language instead of raw positive/negative values.

### Personal-first overview

The current user's position appears before the full group balance.

### Simplification by default

Simplification is ON by default and remembered per group.

### Ledger integrity

Simplification never changes the underlying ledger.

### No phantom transactions

A suggested repayment is not a Settlement until explicitly recorded.

### Partial settlement

Any suggested settlement can be reduced to a partial payment.

### Overpayment allowed

Overpayments generate a warning but can be recorded.

### Settlement confirmation

Recording a settlement requires confirmation.

### Settlement history

Settlement activity records both the financial relationship and who
entered it.

### Recoverable settlements

Deleted settlements can be restored by administrators.

### Offline settlements

Settlements can be recorded offline.

### Independent concurrent settlements

Separate settlement transactions are not treated as conflicting edits.

### Duplicate warning

Suspiciously similar settlements may trigger a warning without being
automatically blocked.

### Immediate recalculation

Balances update locally immediately after every transaction change.

### Group spending

The overview can show total recorded group spending separately from
outstanding balances.
