# TabZero --- User Journey 3 v0.1

## Add Expense → Edit → Delete → History

This document defines the expense creation, editing, deletion,
synchronization, and activity-history experience in TabZero.

The primary goal is to make the common expense flow extremely simple
while preserving a reliable transaction history.

------------------------------------------------------------------------

# 1. Starting an Expense

From a group, the primary action is:

> **\[ + Add Expense \]**

Selecting it opens the expense form directly.

There is no intermediate expense-type menu.

------------------------------------------------------------------------

# 2. Expense Fields

The expense form contains:

> **Add Expense**
>
> What was it? \* `Dinner`
>
> Amount \* `₹2,400`
>
> Paid by `Sayantan ▼`
>
> Split among ☑ Sayantan\
> ☑ Rahul\
> ☑ Priya\
> ☑ Amit
>
> Split ● Equally\
> ○ Unequally
>
> Date `18 Aug 2026`
>
> Note `Great biryani!`
>
> **\[ Save Expense \]**

The exact timestamp is stored internally.

The UI displays only the date by default.

------------------------------------------------------------------------

# 3. Expense Description

The field:

> **What was it?**

is required.

The description is the primary human-readable identifier for an expense.

Example:

> Dinner

> Hotel

> Taxi

> Groceries

A blank expense description is not permitted.

The description supports plain text and emoji.

Rich text is not supported.

If a user pastes formatted content, TabZero converts it to plain text.

------------------------------------------------------------------------

# 4. Amount

The amount is required.

The only valid rule is:

> **Amount \> 0**

Therefore:

-   ₹0 is invalid
-   Negative amounts are invalid
-   Empty amounts are invalid

The group currency is used automatically.

------------------------------------------------------------------------

# 5. Payer

The payer defaults to the current member.

However, any active member can be selected as the payer.

An **Active · Unclaimed** member may also be selected as payer.

This allows a member to record an expense on behalf of somebody who has
not yet connected a device.

Example:

> Rahul --- Active · Unclaimed

Sayantan can record:

> Hotel --- ₹4,000
>
> Paid by: Rahul

------------------------------------------------------------------------

# 6. Participants

By default:

> **All active members are selected.**

This includes:

-   Active claimed members
-   Active unclaimed members

The payer does not have to participate.

Example:

> Sayantan paid ₹1,000.
>
> Split among:
>
> Rahul Priya

This is valid.

------------------------------------------------------------------------

# 7. Archived Members

Archived members are excluded from new expenses.

They cannot be selected as:

-   Payer
-   Participant

Historical transactions remain associated with archived members.

This preserves historical accuracy without allowing archived members to
participate in new financial activity.

------------------------------------------------------------------------

# 8. Payer Does Not Need to Participate

The payer and participants are independent concepts.

Example:

> Sayantan paid ₹1,000 for Rahul and Priya.

Payer:

> Sayantan

Participants:

> Rahul\
> Priya

This is valid.

The UI must not automatically force the payer into the participant list.

------------------------------------------------------------------------

# 9. Participant Requirement

Every expense must contain at least one participant.

An expense with zero participants is invalid.

The Save action must remain unavailable until at least one participant
exists.

------------------------------------------------------------------------

# 10. Equal Split

Equal splitting is the default.

The expense amount is divided equally between all selected participants.

When the amount cannot be divided exactly into the smallest currency
unit, TabZero applies a deterministic rounding rule.

Example:

> ₹100 ÷ 3

Result:

> Participant A --- ₹33.34\
> Participant B --- ₹33.33\
> Participant C --- ₹33.33

The exact allocation order must be deterministic so that different
devices produce the same result.

The underlying total must always equal the original expense amount
exactly.

------------------------------------------------------------------------

# 11. Unequal Split

Selecting:

> **Unequally**

allows the user to specify exact amounts for each participant.

Example:

> Sayantan --- ₹100\
> Rahul --- ₹200\
> Priya --- ₹300

The allocation summary displays:

> **Allocated: ₹600 / ₹600**
>
> **Remaining: ₹0**

The expense cannot be saved until:

> Allocated = Total

If the allocated amount is less than the total:

> **Remaining: ₹50**

If the allocated amount is greater than the total:

> **Over by: ₹50**

The Save action remains unavailable until the allocation exactly matches
the expense total.

------------------------------------------------------------------------

# 12. Removing a Participant During an Unequal Split

If a participant is removed from an unequal split, their allocation is
automatically removed.

No confirmation dialog is required.

Example:

> Rahul --- ₹500

is removed from the participant list.

Rahul's ₹500 allocation is removed immediately.

The remaining allocation is recalculated against the total.

------------------------------------------------------------------------

# 13. Equal → Unequal

When switching from:

> **Equal**

to:

> **Unequal**

TabZero pre-fills the unequal allocations using the current equal split.

Example:

> ₹600 / 3

becomes:

> Sayantan --- ₹200\
> Rahul --- ₹200\
> Priya --- ₹200

The user can then modify the individual amounts.

------------------------------------------------------------------------

# 14. Unequal → Equal

Switching from:

> **Unequal**

to:

> **Equal**

immediately discards the manual allocations and recalculates the split
equally.

No confirmation dialog is shown.

The application deliberately does not warn the user.

> **Let them suffer.**

The new equal allocation becomes the active split.

------------------------------------------------------------------------

# 15. Expense Date

The expense date defaults to the current date.

Users may select any valid date.

Future dates are allowed.

There is no artificial date-range restriction.

The exact creation timestamp remains separately stored.

Example:

> Expense date: 20 Aug 2026
>
> Created at: 18 Aug 2026, 11:42 PM

------------------------------------------------------------------------

# 16. Editing the Expense Date

When editing an expense, the expense date can be changed.

The original creation timestamp remains unchanged.

Example:

> Created: 18 Aug 2026, 11:42 PM
>
> Expense date changed:
>
> 18 Aug → 20 Aug

The edit appears in history.

------------------------------------------------------------------------

# 17. Text and Emoji Rules

TabZero uses plain text throughout the application.

The following can contain:

-   Plain text
-   Emoji

Examples:

-   Member names
-   Group names
-   Group descriptions
-   Expense descriptions
-   Settlement information
-   Optional fields

Only the **Note** field supports new lines.

Nothing supports rich text.

If a user pastes formatted content, TabZero converts it to plain text.

This means:

-   No bold
-   No italics
-   No embedded formatting
-   No HTML
-   No rich-text markup

The data model remains simple and portable.

------------------------------------------------------------------------

# 18. Notes

Notes are optional.

Notes support:

-   Plain text
-   Emoji
-   New lines

Rich text is not supported.

Example:

> `Great biryani! 🍛`
>
> `Paid for the table.`

------------------------------------------------------------------------

# 19. Expense Creator

Every expense records:

> **Created by**

separately from:

> **Paid by**

These are independent fields.

Example:

> Created by: Rahul
>
> Paid by: Sayantan

This distinction is important because a member can record an expense on
behalf of another member.

The product rule is:

> **Created by ≠ Paid by**

They may be the same person, but they do not have to be.

------------------------------------------------------------------------

# 20. Expense Editing Permissions

An expense can be edited by:

### Creator

The member who created the expense can edit it.

### Admin / Super Admin

An administrator can edit any expense in the group.

### Other members

Other members have read-only access to the expense.

------------------------------------------------------------------------

# 21. Editing Someone Else's Expense

If an administrator edits another member's expense, the history clearly
records the action.

Example:

> Rahul created:
>
> **Dinner --- ₹2,000**

Admin Priya changes it to:

> **Dinner --- ₹2,200**

History:

> **Priya edited Rahul's expense**
>
> Dinner
>
> ₹2,000 → ₹2,200

The identity of the person who performed the edit is retained.

------------------------------------------------------------------------

# 22. Expense Deletion

The creator or an administrator can delete an expense.

Before deletion, TabZero displays a confirmation:

> **Delete this expense?**
>
> Dinner --- ₹2,400
>
> This will recalculate the group's balances.
>
> **\[ Cancel \]** **\[ Delete \]**

The user may optionally provide a deletion reason.

The reason is not mandatory.

------------------------------------------------------------------------

# 23. Deleted Expenses

Deleted expenses remain visible in the group's history.

They are not silently erased.

Example:

> ~~Dinner --- ₹2,400~~
>
> **Deleted**
>
> Deleted by Priya · 18 Aug, 9:32 PM

This provides transparency to the group.

The deleted expense is no longer included in the active financial
calculation.

Its historical record remains available.

------------------------------------------------------------------------

# 24. Restoring a Deleted Expense

A deleted expense can be restored.

Restoration is an administrative operation.

Example:

> **Dinner --- ₹2,400**
>
> Status: Deleted
>
> **\[ Restore \]**

Restoring the expense causes it to participate in the group's financial
calculations again.

The restoration itself appears in history.

Example:

> **Priya restored Dinner --- ₹2,400**

------------------------------------------------------------------------

# 25. Editing Deleted Expenses

A deleted expense cannot be edited directly.

It must first be restored.

Flow:

``` text
Deleted Expense
      ↓
   Restore
      ↓
  Active Expense
      ↓
     Edit
```

This keeps the lifecycle unambiguous.

------------------------------------------------------------------------

# 26. Group Activity History

History is a **group-level chronological activity feed**.

It is not limited to individual expense history.

Example:

> **Today**
>
> 9:32 PM --- Priya deleted Coffee ₹320
>
> 9:20 PM --- Rahul added Dinner ₹2,400
>
> 8:15 PM --- Sayantan edited Hotel ₹4,000 → ₹4,500
>
> **Yesterday**
>
> 7:10 PM --- Amit added Taxi ₹800

Each history event should clearly identify:

-   What happened
-   Who performed the action
-   When it happened
-   The relevant object/transaction

------------------------------------------------------------------------

# 27. History Filtering

History supports simple filtering.

Possible filters:

> **All \| Expenses \| Settlements \| Members**

The filter system should remain lightweight.

There is no need for a complex analytics-style activity query system.

Administrative actions can appear naturally within the appropriate
activity category.

------------------------------------------------------------------------

# 28. History Retention

History is retained **forever**.

There is no automatic one-year or multi-year purge.

Historical activity is considered part of the group's data.

JSON exports should preserve relevant history.

This is especially important because TabZero is designed around
portability and auditability.

------------------------------------------------------------------------

# 29. Expenses Screen

In addition to the group activity feed, TabZero has a dedicated:

> **Expenses**

screen.

This screen focuses on actual financial transactions.

A clean group structure can therefore distinguish:

### Overview

Current balances and debts.

### Expenses

Actual expense transactions.

### Activity

Actions performed by group members.

This separation prevents the activity feed from becoming the primary
financial interface.

------------------------------------------------------------------------

# 30. Expense Ordering

Expenses are displayed:

> **Newest first**

by default.

The application may later support alternative sorting, but this is not
required for v0.1.

------------------------------------------------------------------------

# 31. Expense Search

The Expenses screen supports simple local text search.

Example:

> Search: `hotel`

Results can match relevant plain-text fields such as the expense
description and note.

Search is performed locally.

There is no requirement for server-side search infrastructure.

The search should remain intentionally simple and lightweight.

------------------------------------------------------------------------

# 32. Duplicate Expense Detection

TabZero v0.1 does not automatically detect or block duplicate expenses.

If a user enters two identical expenses:

> Dinner --- ₹1,000

and:

> Dinner --- ₹1,000

both may exist.

No automatic warning is required in v0.1.

The user remains responsible for reviewing the expense history.

------------------------------------------------------------------------

# 33. Offline Expense Creation

Expense creation works offline.

A member can create an expense without an active internet connection.

The expense is immediately available locally.

It receives a local synchronization state such as:

> ☁️ Pending sync

The expense remains part of the local transaction ledger.

When connectivity returns, TabZero synchronizes the expense with the
backend.

------------------------------------------------------------------------

# 34. Synchronization State

Synchronization status should be visible but extremely subtle.

Possible states include:

> ☁️ Synced

> ☁️ Syncing...

> ☁️ Pending

> ⚠️ Waiting for connection

The application should not feel like a cloud-management application.

The indicator exists only to reassure the user that their local changes
are understood and tracked.

------------------------------------------------------------------------

# 35. Offline Expenses from Multiple Members

Multiple members can create expenses while offline.

Example:

> Rahul offline → Dinner ₹500
>
> Priya offline → Taxi ₹700

When both devices reconnect, both transactions should be synchronized
and merged into the group.

The system must not overwrite one transaction merely because another
device synchronized first.

Each transaction should have its own stable identity.

The transaction ledger therefore supports independent synchronization of
expenses.

------------------------------------------------------------------------

# 36. Concurrent Offline Editing

A more complex situation occurs when two devices edit the same expense
while offline.

Example:

Original:

> Dinner --- ₹2,000

Rahul edits offline:

> ₹2,500

Priya edits offline:

> ₹2,200

When the devices reconnect, the system detects a conflict.

TabZero must **not silently choose a winner**.

Instead, the conflict is surfaced for administrative resolution.

Example:

> ⚠️ **Conflict detected**
>
> Dinner was edited on another device.
>
> **Version A**
>
> ₹2,500
>
> Edited by Rahul
>
> **Version B**
>
> ₹2,200
>
> Edited by Priya
>
> **\[ Keep A \]** **\[ Keep B \]** **\[ Review \]**

Only an Admin/Super Admin can resolve the conflict.

The final resolution is itself recorded in history.

------------------------------------------------------------------------

# 37. Conflict Resolution Principle

TabZero prefers:

> **Explicit conflict resolution**

over:

> **Silent last-write-wins**

for important financial transactions.

The system should never silently discard a member's financial edit
merely because another device synchronized later.

------------------------------------------------------------------------

# 38. Transaction Identity

Every expense must have a stable unique transaction identity.

This is required for:

-   Offline creation
-   Synchronization
-   Duplicate prevention at the data layer
-   Editing
-   Deletion
-   Restoration
-   Conflict detection

The same principle applies to settlements and other transaction types.

------------------------------------------------------------------------

# 39. Balance Recalculation

Any change to an active financial transaction can affect balances.

Examples:

-   Add expense
-   Edit expense
-   Delete expense
-   Restore expense
-   Add settlement
-   Edit settlement
-   Delete settlement

TabZero recalculates the derived balances from the transaction ledger.

Balances are never manually edited.

------------------------------------------------------------------------

# 43. Journey 3 Product Rules

Journey 3 establishes these rules:

### Simplicity

The normal expense flow should require minimal interaction.

### One payer

Every expense has exactly one payer.

### Flexible participation

The payer does not need to participate.

### Active members only

Archived members cannot participate in new expenses.

### Unclaimed members are fully usable

Unclaimed members can be payers and participants.

### Exact accounting

Allocations must always equal the expense total.

### Deterministic rounding

Equal splits use a deterministic smallest-unit rounding rule.

### Plain text

All user-entered fields use plain text and emoji.

### Notes are special

Only notes support new lines.

### Creator tracking

Created by and paid by are separate concepts.

### Transparent editing

Edits identify the person who made them.

### Recoverable deletion

Deleted expenses can be restored.

### Permanent history

Activity history is retained forever.

### Offline-first transaction creation

Expenses can be created offline.

### Explicit financial conflict resolution

Concurrent offline edits are surfaced rather than silently overwritten.

### Lightweight synchronization

Sync status is visible but intentionally subtle.
