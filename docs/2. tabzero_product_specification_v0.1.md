# TabZero --- Product Specification v0.1

**Tagline:**\
\### *Split bills, clear the tab. Keep the app free.*

**Product personality:** Minimal with subtle sarcasm.

------------------------------------------------------------------------

## 1. Product Intent

TabZero is a free, accountless, lightweight expense-splitting
application for groups.

Its purpose is deliberately narrow:

> **Record shared expenses, calculate debts, simplify repayments, and
> settle them.**

TabZero should not become a personal finance application.

There will be:

-   No user accounts
-   No subscriptions
-   No expense categories
-   No advertisements
-   No recurring expenses
-   No receipt management
-   No payment gateway
-   No currency conversion
-   No unnecessary analytics

The product should remain **small, fast, inexpensive to host, and easy
to understand.**

------------------------------------------------------------------------

# 2. Architecture Philosophy

TabZero will use a **lightweight cloud-assisted architecture**.

There is no traditional user account system.

Instead, each installation can have a lightweight, randomly generated
device identity.

The backend exists primarily to allow members of a group to
share/synchronize group data.

The server should store **only what is necessary to facilitate group
synchronization and membership**.

The architecture should aggressively minimize:

-   CPU usage
-   RAM usage
-   database size
-   bandwidth
-   background processing
-   third-party services

The objective is:

> **A useful backend that can run cheaply enough to keep TabZero free.**

The exact synchronization protocol and backend technology will be
designed separately.

------------------------------------------------------------------------

# 3. Identity Model

TabZero deliberately separates:

### Person

A logical member inside a group.

Example:

> Rahul

### Device

A physical installation of TabZero.

### Membership

The relationship between a person and a group.

This means a person can exist in a group before they ever install
TabZero.

For example, an admin can create:

> Sayantan\
> Rahul\
> Priya\
> Amit

Only Sayantan may initially have TabZero installed.

The others remain valid group members without accounts.

------------------------------------------------------------------------

# 4. Groups

Users can create unlimited groups.

A group contains:

-   Name
-   Currency
-   Members
-   Expenses
-   Settlements
-   Administrators
-   Super Admin
-   Invite mechanism
-   Activity/history
-   Creation information
-   Active/archived state

### Currency

Each group has exactly **one currency**.

Examples:

> Goa Trip → INR

> London Trip → GBP

Automatic currency conversion is not supported.

Multiple currencies within the same group are not supported.

------------------------------------------------------------------------

# 5. Group Visibility

Groups are **not publicly searchable**.

Instead, they use invitation links.

Possession of the invite link allows someone to request access.

The group itself remains private.

Conceptually:

> **Private group + shareable invitation**

Invite links should use sufficiently random tokens and should be
regeneratable/revocable.

------------------------------------------------------------------------

# 6. Roles

There are two administrative levels.

## Super Admin

The person who created the group.

The Super Admin has the same day-to-day permissions as an Admin.

The special distinction is **ownership**.

The Super Admin can:

-   Promote members to Admin
-   Transfer Super Admin ownership
-   Perform all Admin operations

The Super Admin does not have additional expense-management powers
merely because they are Super Admin.

------------------------------------------------------------------------

## Admin

Admins have the same operational permissions as the Super Admin.

They can:

-   Manage members
-   Approve join requests
-   Approve member identity claims
-   Manage invitations
-   Edit/delete any expense
-   Delete settlements
-   Perform administrative actions
-   Archive/manage the group

The Super Admin can promote multiple members to Admin.

------------------------------------------------------------------------

# 7. Super Admin Transfer

If the Super Admin wants to leave the group:

> They **must first transfer Super Admin ownership** to another member.

They cannot simply leave and leave the group without a Super Admin.

If an ordinary Admin leaves:

> No transfer is necessary.

Another Admin remains available.

------------------------------------------------------------------------

# 8. Joining a Group

The basic journey:

``` text
Invite Link
    ↓
Group Preview
    ↓
Are you already a member?
    ├── Yes
    │    ↓
    │  Select existing member
    │    ↓
    │  Claim request
    │    ↓
    │  Admin approval
    │
    └── No
         ↓
       Enter name
         ↓
       New-member request
         ↓
       Admin approval
```

Before approval, the prospective member does **not** see the group's
member list.

They should only see enough information to understand which group
they're requesting access to.

------------------------------------------------------------------------

# 9. Existing Member Claim

Suppose the group already contains:

> Rahul

Rahul installs TabZero and follows the invite.

He selects:

> **I'm already a member**

and requests to claim:

> Rahul

The administrators receive the request.

If multiple devices attempt to claim Rahul:

> **All relevant requests remain visible to the administrators.**

An administrator decides which request should be associated with Rahul.

This avoids automatic identity takeover.

------------------------------------------------------------------------

# 10. Multiple Devices

A single member can have multiple approved devices.

Example:

> Rahul --- Phone\
> Rahul --- Tablet

The administrator can approve additional devices when necessary.

This is particularly important for:

-   Phone replacement
-   Reinstallation
-   Tablet usage
-   Device migration

------------------------------------------------------------------------

# 11. Member Lifecycle

Members can be:

-   Active
-   Pending
-   Archived

Historical transactions must retain their member references.

A member should therefore not simply disappear because they leave the
group.

Archiving preserves historical integrity.

------------------------------------------------------------------------

# 12. Expenses

An expense consists of:

### Required

-   Description
-   Amount
-   Payer
-   Participants
-   Split method

### Optional

-   Date/time
-   Note

There are **no categories**.

------------------------------------------------------------------------

# 13. Adding an Expense

Any active member can add an expense.

Default behavior:

-   Current member is initially selected as payer
-   All active members are selected
-   Equal splitting is selected
-   Current date/time is selected

Example:

> **Dinner**\
> ₹2,400
>
> Paid by: Sayantan
>
> Split among:
>
> ☑ Sayantan\
> ☑ Rahul\
> ☑ Priya\
> ☑ Amit
>
> Split:
>
> ● Equally\
> ○ Unequally

------------------------------------------------------------------------

# 14. Payer Does Not Need to Participate

The payer may be excluded from the split.

Example:

> Sayantan paid ₹1,000 for Rahul and Priya.

Participants:

> ☐ Sayantan\
> ☑ Rahul\
> ☑ Priya

This is valid.

------------------------------------------------------------------------

# 15. One Payer Per Expense

An expense has exactly **one payer**.

Multiple people cannot jointly pay a single expense.

If necessary:

> ₹2,000 paid by Sayantan\
> ₹2,000 paid by Rahul

should be recorded as two separate expenses.

This keeps the transaction model simple.

------------------------------------------------------------------------

# 16. Split Methods

## Equal

The default.

The expense is divided equally among selected participants.

## Unequal

Users manually specify exact amounts.

Example:

> Sayantan --- ₹100\
> Rahul --- ₹200\
> Priya --- ₹300

The sum must equal the expense total.

### Not supported

-   Percentages
-   Shares
-   Ratios

at least in v0.1.

------------------------------------------------------------------------

# 17. Zero-Value Participants

A participant cannot have a zero-value allocation in an unequal split.

If someone owes nothing, they should simply be removed from the
participant list.

------------------------------------------------------------------------

# 18. Expense Editing

An expense can be edited only by:

-   Its creator
-   An Admin/Super Admin

A normal member cannot edit somebody else's expense.

Every edit should be visible in the group's history.

------------------------------------------------------------------------

# 19. Expense Deletion

An expense can be deleted by:

-   Its creator
-   Admin
-   Super Admin

Deletion must appear in the activity/history system.

The underlying transaction model should preserve enough information to
maintain consistency and auditability.

------------------------------------------------------------------------

# 20. Expense History

History is an important part of TabZero.

Examples:

> Sayantan added **Dinner --- ₹2,400**

> Rahul edited **Dinner --- ₹2,400 → ₹2,600**

> Priya deleted **Coffee --- ₹320**

The history should make it clear:

-   What happened
-   Who performed the action
-   When it happened

This becomes especially important because there are no accounts and
because multiple people can modify the same group.

------------------------------------------------------------------------

# 21. Settlements

Settlements are first-class transactions.

Example:

> Rahul → Sayantan\
> ₹500

A settlement means:

> **Money was paid back between members.**

It does not require integration with UPI, banks, or payment gateways.

------------------------------------------------------------------------

# 22. Partial Settlements

Partial settlement is supported.

Example:

Rahul owes Sayantan:

> ₹500

Rahul pays:

> ₹300

TabZero records:

> Rahul → Sayantan ₹300

Remaining debt:

> ₹200

------------------------------------------------------------------------

# 23. Suggested Settlements

TabZero should automatically determine useful settlement relationships.

If:

> Rahul owes Sayantan ₹600

the **Settle Up** action should automatically propose:

> Rahul → Sayantan\
> **₹600**

The user should not normally have to manually determine who owes whom.

------------------------------------------------------------------------

# 24. Overpayment

If someone attempts:

> Rahul owes Sayantan ₹500

but records:

> Rahul → Sayantan ₹700

TabZero should **warn but allow** it.

The resulting balance may legitimately become:

> Sayantan owes Rahul ₹200

This accommodates real-world situations such as:

-   Paying back extra
-   Covering another expense
-   Rounding
-   Informal reimbursements

------------------------------------------------------------------------

# 25. Settlement Deletion

Settlements can be deleted by:

-   Their creator
-   Admin
-   Super Admin

Deletion must appear in history.

------------------------------------------------------------------------

# 26. Settlement Notifications

Users can optionally send a notification associated with a settlement.

Example:

> **Rahul has been notified that ₹500 was marked as settled.**

Notifications are not intended to become a social/chat system.

They exist only for actionable events.

------------------------------------------------------------------------

# 27. Notifications

TabZero should use notifications sparingly.

Notifications are primarily for things requiring action.

Examples:

> **Rahul wants to join Goa Trip.**

> **Rahul wants to claim the existing member Rahul.**

> **Sayantan approved your membership request.**

> **Priya sent you a settlement notification.**

TabZero should **not** send unnecessary engagement notifications such
as:

> "You spent ₹800 today!"

> "You haven't opened TabZero in 3 days!"

> "Check your finances!"

The app should never manufacture engagement.

------------------------------------------------------------------------

# 28. Balance Calculation

Balances are always derived from the transaction ledger.

Conceptually:

``` text
Expenses
+
Settlements
      ↓
Net Member Balances
      ↓
Debt Relationships
```

The application must not treat manually stored balances as the source of
truth.

------------------------------------------------------------------------

# 29. Simplify Debts

**Simplify Debts = ON by default.**

Users can disable it.

When enabled, TabZero calculates a reduced set of repayments across the
entire group.

Example:

Instead of:

> A → B ₹500\
> B → C ₹300\
> C → A ₹100

TabZero can calculate a smaller set of transactions that produces the
same final result.

The underlying expenses and settlements remain unchanged.

Simplification affects the **recommended repayment view**, not the
transaction history.

------------------------------------------------------------------------

# 30. Raw vs Simplified View

Users should be able to turn simplification off.

### Simplified

Shows the minimum practical repayment relationships.

### Un-simplified

Shows the direct debt relationships resulting from the underlying
transactions.

This provides transparency for users who want to understand exactly how
the balance was derived.

------------------------------------------------------------------------

# 31. JSON Export

Any member can export a group.

The export contains the information necessary to reconstruct the group
snapshot, including:

-   Group metadata
-   Currency
-   Members
-   Roles
-   Membership state
-   Expenses
-   Settlements
-   Relevant history
-   Schema/version information

Export is not restricted to administrators.

------------------------------------------------------------------------

# 32. JSON Import

Imported JSON is **always read-only**.

Example:

> **Goa Trip 2026**
>
> Imported snapshot
>
> 🔒 Read-only

Users can inspect:

-   Members
-   Expenses
-   Settlements
-   Balances
-   History

but cannot directly modify the imported snapshot.

------------------------------------------------------------------------

# 33. Clone

A read-only imported group can be cloned.

The clone copies everything initially:

-   Group information
-   Members
-   Expenses
-   Settlements
-   History

The clone is then an independent editable group.

Example:

``` text
Goa Trip 2026.json
        ↓
     Import
        ↓
   Read-only
        ↓
      Clone
        ↓
Goa Trip 2027
```

------------------------------------------------------------------------

# 34. Reinstallation / Data Recovery

There are two recovery paths.

### Personal backup

``` text
Export JSON
     ↓
Reinstall
     ↓
Import JSON
```

The imported snapshot remains read-only.

### Group recovery

``` text
Reinstall
     ↓
Join group via invite
     ↓
Claim existing member
     ↓
Admin approval
     ↓
Member restored on new device
```

Both mechanisms are supported.

------------------------------------------------------------------------

# 35. Currency

One group = one currency.

Supported example:

> Goa Trip → INR

> Japan Trip → JPY

No automatic currency conversion.

Multiple currencies in a single group are not supported.

------------------------------------------------------------------------

# 36. Explicitly Out of Scope

TabZero v0.1 does **not** include:

-   User accounts
-   Passwords
-   Social profiles
-   Expense categories
-   Recurring expenses
-   Multiple currencies per group
-   Currency conversion
-   Multiple payers per expense
-   Percentage splits
-   Share-based splits
-   Receipt attachments
-   Photos
-   Expense comments
-   Chat
-   Budgets
-   Financial analytics
-   Bank synchronization
-   UPI integration
-   Payment gateways
-   Ads
-   Paid tiers
-   Subscriptions

------------------------------------------------------------------------

# 37. Product Personality

TabZero should be:

> **Minimal with subtle sarcasm.**

The interface itself should remain clean and serious.

Occasional copy can have personality.

For example:

> **₹1,240 outstanding**\
> Apparently friendship has a balance sheet.

Or:

> **All settled.**\
> Miracles do happen.

But the application should never become a comedy app.

The product's personality should support the experience rather than
interfere with it.

------------------------------------------------------------------------

# 38. Core Product Rule

A proposed feature should be questioned against one simple test:

> **Does this make it easier to answer "Who owes whom, and how much?"**

If not, it probably doesn't belong in TabZero's core.

------------------------------------------------------------------------

# 39. v0.1 Product Definition

At this point, TabZero can be summarized as:

> **An accountless, local-first, cloud-assisted, lightweight expense
> ledger where groups are joined through invitation links, members can
> exist without accounts, expenses are manually recorded and split,
> debts are automatically calculated and simplified, settlements can be
> recorded, and the entire group can be exported as portable JSON.**

And the product promise:

> **Split bills, clear the tab. Keep the app free.**

------------------------------------------------------------------------

## The next phase

I think we're now ready for the **really interesting part: the user
journeys and edge cases**.

I'd suggest we *not* attack all 32 decisions at once. We'll walk through
TabZero as if we're actually using it:

**Journey 1 --- First launch → Create a group → Add members**

Then:

**Journey 2 --- Another person joins → New member vs existing member**

Then:

**Journey 3 --- Add expense → Edit → Delete → History**

Then:

**Journey 4 --- Balances → Simplify → Settle → Partial settlement**

Then:

**Journey 5 --- Admin/member lifecycle**

Then:

**Journey 6 --- Offline/sync/conflicts/reinstallation**

Then finally we'll create an **edge-case matrix**. That last one is
where we'll catch things like *"What happens if two admins edit the same
expense while offline?"* before we ever write a line of code.
