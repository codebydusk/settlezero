# SettleZero --- User Journey 2 v0.1

## Invite → Join → New Member vs Existing Member

This document defines how people discover, join, claim membership in,
and gain access to a SettleZero group.

The journey is intentionally designed around SettleZero's accountless
identity model.

------------------------------------------------------------------------

## 1. Opening an Invite Link

When a user receives a SettleZero group invite:

> **SettleZero invite --- Goa Trip 2026**

the link should behave as follows:

### If SettleZero is installed

The link opens SettleZero directly and passes the invitation context into
the app.

### If SettleZero is not installed

The user is taken through a lightweight web fallback that can direct
them to install SettleZero.

After installation, the invite context should be recoverable so the user
can continue the joining process without having to manually find or copy
the link again.

The invite link itself remains the entry point to the group.

------------------------------------------------------------------------

# 2. Invite Preview

Before requesting membership, the prospective member sees a lightweight
group preview.

The preview contains:

-   Group name
-   Group description, if present
-   Group currency
-   Inviter

Example:

> **You're invited to**
>
> # Goa Trip 2026
>
> Weekend trip with the gang.
>
> **Currency:** ₹ INR
>
> Invited by: Sayantan
>
> **\[ Join Group \]**

The prospective member does **not** see:

-   Member list
-   Member names
-   Member count
-   Group balances
-   Group expenses
-   Group history

This preserves group privacy before membership is approved.

------------------------------------------------------------------------

# 3. Existing vs New Member

Selecting **Join Group** presents a single decision screen:

> **Are you already a member of Goa Trip 2026?**
>
> **\[ Yes, I'm already a member \]**
>
> **\[ No, I'm new to this group \]**

This is the primary branching point of the membership journey.

------------------------------------------------------------------------

# 4. New Member Flow

A person who selects:

> **I'm new to this group**

is asked for their name.

Example:

> **What's your name?**
>
> `Rahul`
>
> **\[ Send Join Request \]**

The request enters a pending state.

The prospective member sees:

> **Waiting for approval**
>
> An admin of Goa Trip 2026 needs to approve your request.

The user can safely close the application.

The pending request remains visible when they return to SettleZero.

A notification may be delivered when the request is approved or
rejected.

------------------------------------------------------------------------

# 5. Pending Requests

Pending membership requests should be visible to the requesting user.

The user should be able to see:

-   Group name
-   Requested name
-   Request status
-   Request time
-   Current state

Example:

> **Goa Trip 2026**
>
> Requested as: Rahul
>
> **Status: Waiting for approval**

The application should not require the user to keep SettleZero open while
waiting.

------------------------------------------------------------------------

# 6. Admin View of New-Member Request

When an administrator opens SettleZero, a pending request should be visible
as an actionable notification/request.

Example:

> 🔔 **Membership request**
>
> Rahul wants to join **Goa Trip 2026**
>
> Requested 2 minutes ago.
>
> **\[ Approve \]** **\[ Reject \]**

The information shown to the administrator should remain minimal.

The administrator does not need unnecessary device information such as:

-   Phone model
-   Hardware details
-   Operating-system details

unless such information is later proven useful for troubleshooting.

------------------------------------------------------------------------

# 7. Existing Member Claim Flow

Suppose the administrator previously created:

> Rahul

with state:

> **Active · Unclaimed**

Rahul installs SettleZero and follows the group invite.

He selects:

> **Yes, I'm already a member**

He is then asked to enter the name under which he believes he was added.

Example:

> **Enter the name you were added with**
>
> `Rahul`
>
> **\[ Request Membership \]**

The joining user is **not shown the group member list**.

SettleZero submits the information to the group.

An Admin then maps the request against an existing member.

The joining user does not receive a confirmation that a matching member
exists before administrative approval.

------------------------------------------------------------------------

# 8. Admin Mapping of Existing Member

An existing-member claim request appears to administrators as:

> 🔔 **Membership claim request**
>
> Requester's name: **Rahul**
>
> **\[ Select existing member \]**
>
> **\[ Approve \]** **\[ Reject \]**

The administrator chooses which existing member identity should be
associated with the requesting device.

If the administrator determines that the requester corresponds to:

> Rahul · Active · Unclaimed

the administrator approves that mapping.

The device then becomes associated with that existing member identity.

------------------------------------------------------------------------

# 9. Multiple Possible Matches

If an administrator needs to choose between multiple possible member
identities, the administrator should be able to select the appropriate
existing member.

For example:

> Possible existing members:
>
> Rahul Rahul Roy Rahul S.

The requester is not given the complete group member list.

The administrator is responsible for resolving the identity.

------------------------------------------------------------------------

# 10. Multiple Devices Claiming the Same Member

Multiple devices may request the same member identity.

Example:

> Rahul --- Device A --- Pending
>
> Rahul --- Device B --- Pending

The administrators can see both requests.

The member remains:

> **Active · Unclaimed**

until one request is approved.

Once an administrator approves one request:

> Rahul --- **Active**

The approved device becomes associated with Rahul.

Other pending claims can then be rejected.

The system must not automatically assign the identity to the first
requester.

------------------------------------------------------------------------

# 11. Rejected Claim

If an administrator rejects an existing-member claim, the requester is
not permanently blocked.

They may:

-   Submit another claim
-   Request membership as a new member
-   Correct a mistaken name and try again

Example:

> **Your membership claim was rejected.**
>
> **\[ Try Again \]**
>
> **\[ Request as New Member \]**

This prevents an accidental administrative rejection from permanently
preventing legitimate membership.

------------------------------------------------------------------------

# 12. Existing Member with Historical Expenses

Suppose the group already contains:

> Rahul --- Active · Unclaimed

and Rahul has existing historical transactions.

For example:

> Dinner --- ₹2,000\
> Rahul's share: ₹500

Rahul later claims the existing member identity.

Nothing about the group's financial history changes.

The following remain attached to Rahul:

-   Historical expenses
-   Expense participation
-   Balances
-   Settlements
-   Activity/history

The device association is simply added to the existing member identity.

------------------------------------------------------------------------

# 13. Attempting to Join as New Member When a Similar Name Exists

Names are not treated as globally unique identities.

However, SettleZero should prevent accidental duplicate member names within
a group.

Example:

Existing member:

> Rahul

A new requester attempts:

> Rahul

SettleZero should prevent creation of another active member with the exact
same name.

Instead, the user should be asked to choose a distinct name.

For example:

> **A member named Rahul already exists.**
>
> Please choose another name.
>
> Examples:
>
> `Rahul1`
>
> `Rahul R`
>
> `Rahul Roy`

Nicknames are explicitly acceptable.

This is a deliberate product decision because duplicate names could
cause people to accidentally assign expenses to the wrong person.

The same rule applies when administrators manually add members.

------------------------------------------------------------------------

# 14. Multiple Administrators

If a group contains:

> Sayantan --- Super Admin\
> Priya --- Admin\
> Amit --- Admin

any administrator can process membership requests.

A request does not require approval from the Super Admin specifically.

------------------------------------------------------------------------

# 15. Concurrent Approval

If two administrators attempt to approve the same request
simultaneously:

> Priya → Approve
>
> Amit → Approve

the backend must handle the operation as **atomic and idempotent**.

Exactly one membership transition should occur.

The second administrator should receive a harmless result such as:

> **This request has already been approved.**

No duplicate membership should be created.

This is an implementation requirement arising directly from the product
behavior.

------------------------------------------------------------------------

# 16. Rejection Reason

Rejecting a membership request does not require a reason.

However, the administrator is given an optional:

> **Reason**

field.

Example:

> Reason: `You're not the Rahul from our trip.`

The field is optional.

If provided, the reason may be shown to the requester.

------------------------------------------------------------------------

# 17. Revoked Invite

If a user opens an invite that has been revoked or regenerated:

> **This invitation is no longer valid.**
>
> Please obtain a new invite link from a group administrator.

The old invitation cannot be used to request membership.

This applies even if the user opened the invitation before it was
revoked but attempts to submit the request afterward.

------------------------------------------------------------------------

# 18. Invite Expiration

Invite links do not automatically expire.

They remain valid until an administrator:

-   Revokes them
-   Regenerates the invitation

This keeps the system lightweight and avoids unnecessary expiration
infrastructure.

------------------------------------------------------------------------

# 19. Archived Groups

If someone opens an invitation to an archived group:

> **This group is archived and no longer accepts new members.**

No new membership request can be created.

Existing members can continue to access the archived group according to
the group's archived-state rules.

------------------------------------------------------------------------

# 20. Existing Member Opens Invite Again

If an already-approved member opens the same group's invite link:

> **You're already a member of Goa Trip 2026.**
>
> **\[ Open Group \]**

No new membership request is generated.

------------------------------------------------------------------------

# 21. Connectivity Requirement

Joining a group requires internet connectivity.

The following operations require connectivity:

-   Submitting a new-member request
-   Submitting an existing-member claim
-   Receiving administrative membership decisions
-   Synchronizing membership state
-   Synchronizing group data

Local-only operations remain available offline.

The invite link itself can be opened without necessarily completing the
membership process offline, but the actual membership request cannot be
finalized until the device can communicate with the backend.

------------------------------------------------------------------------

# 24. Journey 2 Product Rules

Journey 2 establishes these rules:

### Privacy

Prospective members cannot see the group member list before approval.

### No automatic identity takeover

Existing-member claims always require administrator mapping/approval.

### Multiple devices

A member may have multiple approved devices.

### Duplicate names

Exact duplicate active member names are not allowed within a group.

### Administrative flexibility

Any Admin or Super Admin can approve membership requests.

### Safe concurrency

Membership approval must be atomic and idempotent.

### Revocable invitations

Invite links remain valid until explicitly revoked or regenerated.

### Archived groups reject new members

Archived groups cannot accept new membership requests.

### Offline boundaries

Membership operations require connectivity; local group operations do
not.
